Method: public web pages, GitHub repository pages, the GitHub REST API (repo metadata), and the PyPI JSON API. We did not install, run, scan or connect to any third-party tool or MCP server. Star counts and "last push" dates come from `api.github.com/repos/<owner>/<repo>` on 2026-11-05 and are only rough signals. "Does NOT do" means *the project's public docs/README do not describe this feature*. It does not mean we proved the feature is absent. Re-check before quoting publicly.

## 2. Our differentiation (honest)

**Already covered by others. We should not claim novelty for these:**
- **Tool-poisoning, shadowing and rug-pull scanning** is mainstream: Snyk Agent Scan, Cisco mcp-scanner, MCP-Shield, and Pipelock all do it.
- **Tool pinning and rug-pull detection** exists in several places. The old mcp-scan hashed descriptions. mcpseal, mcp-warden and mcplock keep lockfiles, and mcpseal already hashes name, description and **input schema**. "Lockfile of tool definitions" is not new in late 2026.
- **Runtime proxy with deny rules and audit** exists in Pipelock, mcpwall, Lasso, Docker MCP Gateway, mcp-guardian and ToolHive.
- **Argument-level rules** exist in mcpwall (regex, glob, path `not_under`), Pipelock (built-in rules and DLP), and ToolHive (Cedar).
- **Human approval** exists in mcp-guardian.
- **A public detection corpus** exists: Pipelock's `agent-egress-bench`.

**The real gap. No single project we found combines all of these:**
1. **Full-schema pinning that covers the whole server-returned tool object.** That means annotations, `outputSchema`, titles, nested parameter descriptions, enum and default values, not just name, description and inputSchema. It should come with a human-readable **diff** on drift, enforced **at runtime in the proxy**, and keep the same lockfile usable in CI. mcpseal pins at runtime but with a narrower field set and no diff UX described. mcp-warden pins in CI, and its runtime proxy is stdio-only.
2. **Declarative, enforced argument policy with typed constraints** (path allowlists with canonicalisation and symlink handling, domain/URL allowlists, regex), per server and per tool. It should have **enforce and monitor modes** and human confirmation, over **both stdio and Streamable HTTP**. mcpwall is stdio-only and has no domain allowlist. mcp-warden's YAML policy is design-time only. Pomerium and Microsoft gateways stop at the tool-name level.
3. **Explainable static detection.** Each finding should say why it scored (risk score breakdown), and coverage should include **invisible Unicode** and **name collisions** across servers.
4. **Audit in JSONL and OpenTelemetry with secret masking**, mapped to EU AI Act Art. 12/19/26 log-keeping language (see SOURCES.md).
5. **A reproducible, published benchmark** that reports detection rate, false-positive rate and proxy latency overhead against a versioned attack corpus. Pipelock has a corpus but does not auto-publish scores, per its README. None of the others publish numbers.
6. **Local-first and lightweight.** One `pip`/`uvx` install with no Docker, no Kubernetes, no cloud account and no API key. Snyk and Cisco need cloud APIs for their main features. Docker, ToolHive, Microsoft and ContextForge need container or K8s infrastructure.

Positioning sentence: *"The local, dependency-light MCP proxy that pins every tool's full schema, enforces argument-level policy, and proves its detection and overhead with a reproducible benchmark."* Pipelock is the project to benchmark against and to be transparent about. Mention that it is broader (egress, A2A, DLP), while we go deeper on schema integrity and declarative argument policy in Python.
